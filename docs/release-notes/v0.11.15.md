# AI Chat Shell Exec v0.11.15

This release makes first-conversation URL assignment recovery host-independent and adds exact M365 route coverage.

## M365 first-conversation routes

- M365 may change a newly opened conversation from `/chat` to `/chat/<UUID>` while the first helper is still rendering, while its backend request is running, or after the result has already been written into the Lexical composer.
- The extension now recognizes that route shape without a host-name exception. It carries the operation only when the same latest explicit user message, adjacent assistant response, exact helper payload, and proved turn ownership remain current. M365 requires the original DOM roots; ChatGPT alone may rebind a uniquely matching replacement turn through stable message IDs.
- A recognized assignment enters a minimum four-second reconciliation window. Automatic backend starts, local preview commits, composer writes, and sends remain blocked until the route is both scan-settled and stable for the whole window.
- A fully rendered helper cannot be lost merely because the scanner was awaiting its outer local-state/settings read when the host changed only the URL. Live proof is captured at generation time, revalidated against the unchanged authored turn, and the extension schedules its own post-quarantine scan without relying on another DOM mutation. When ChatGPT uniquely rebinds stable message IDs, the replacement root also inherits the original processed claim, so releasing a shell or Skill backend lock cannot dispatch it again.
- A result already written into a redrawn M365 composer is never inserted again. If the complete plugin-owned text remains exact, delivery resumes with the original send behavior only.
- Skill `load` uses the same route ownership proof, so a complete helper arriving immediately after M365 assigns the UUID route is processed and returned once.

## Safety boundaries

- The URL is a trigger for ownership reconciliation, not proof by itself.
- Query/hash changes, cross-origin navigation, a permanent UUID conversation changing to another UUID, unproved transcript replacement, a later/reordered user turn, detached helper roots, and copied M365 content in replacement nodes are rejected.
- Work that already started may finish locally, but its result cannot enter a conversation that no longer contains the exact originating turn.
- A tentative claim waiting on settings, approval, profile, or pending-state work is not execution. If the URL is assigned before the backend request starts, that claim is released to one settled retry and is never restored as already processed.
- Restored unsubmitted output has no live DOM proof and remains unable to migrate across routes. Submitted output may move only to finish its server presentation receipt.
- Manual Force run remains bound to the lifecycle in which the trusted click occurred.
- The five send-actuator functions remain byte-identical to v0.8.6 and v0.8.9.

## Regression coverage

- Focused unit tests cover positive M365 `/chat` to UUID rebinding, permanent UUID A-to-B rejection, query-only rejection, same-text M365 replacement-DOM rejection, stable-ID ChatGPT redraw recovery, duplicate stable-ID rejection, backend-in-flight Skill route replacement with exactly one request/reply, completed-then-rerendered helpers staying processed, pre-backend claims remaining retryable, and exact same-semantic observer redraw ownership for both shell and Skill dispatch.
- Independent unpacked-Chrome pages cover a completed shell helper and installed Skill load paused on the outer settings read followed by URL-only `pushState`, an in-flight real tmux command, an exact post-write Lexical composer redraw with send-only recovery, immediate and delayed transcript replacement, route replacement after the first composer write, permanent-to-permanent route rejection, a Skill load whose final helper content arrives after UUID assignment, and a replaced Skill turn that must dispatch zero times.
- Every positive case asserts exactly one runtime request, backend marker execution, composer write where applicable, and submitted result. Negative cases assert zero backend requests when work has not started, no composer or submitted-message leak, and an empty pending queue after settlement.
