# AI Chat Shell Exec v0.11.8

This release fixes a Skill dispatch race in newly created chats and adds an explicit recovery path without weakening the initial-history or Skill protocol boundaries.

## Fixed

- A live assistant Skill `load` response can no longer stop after appearing only in **Detected helper block (debug)**. When the extension observes assistant generation in the current new-chat lifecycle, the first stable Skill helper proceeds to the existing background/server load path and its result enters the durable composer-delivery queue.
- Generation epochs retain the semantics that were already historical when generation began. A framework that clears an old Skill helper and restores it in a later observer batch during an unrelated response cannot reclassify it as live or auto-load it.
- A second Skill helper that finishes rendering while another Skill request is still finalizing is rescanned after the single-flight lock is released instead of waiting indefinitely for an unrelated DOM mutation.
- Skill backend results are bound to the originating page lifecycle and exact rendered helper. A response cannot enter a different chat after navigation, while a retained same-root URL handoff is reclaimed exactly once after a React redraw.
- Pending agent prompts defer newly detected Skill helpers without marking or consuming them, then release them to the normal scan path after the composer is available.
- The Debug view now separates parse success from dispatch state by showing the history baseline, candidate-bound live-generation evidence, Skill in-flight state, and contextual recovery availability.

## Recovery and safety

- Cold-start and reloaded conversation history still does not auto-execute. If a complete unhandled assistant Skill helper is present without live-generation evidence, the compact panel exposes a separate **Process Skill** action. It calls the same strict id/SHA/challenge validation path; Skill helpers never enter executable Force run or duplicate bypass.
- Explicit user messages, M365 user-message roots, plugin-owned `skill-output`/`shell-output`, and already processed Skill helpers cannot expose that recovery action.
- Force run and Process Skill are single-flight and remain unavailable while the assistant is generating, a Skill/backend call or result delivery is active, an unsent agent prompt owns the composer, a shell helper is active, or incompatible manual work is pending. Only the action matching the latest eligible helper is shown.
- Force run is bound to the exact page lifecycle and DOM-latest executable helper through the final awaited preflight. A changed helper, changed chat route with retained old DOM, newer Skill action, or stale click during another backend helper call cancels without queuing or contacting the backend.

## Tests

- Added focused dispatch tests for candidate-bound generation evidence, cold-history and single/two-phase same-root redraw safety, later live reuse of the same payload, cross-chat backend-response rejection, route-await aborts, agent-composer deferral, unambiguous manual actions, user/plugin-output rejection, and Skill single-flight wake-ups.
- Added real unpacked-Chrome cases in separate tabs for live new-chat auto-load, queued-result route recovery, cold-history redraw/manual recovery, stale old-route Stop-control rejection, and user-message rejection. The original full-page Chrome E2E remains intact.
