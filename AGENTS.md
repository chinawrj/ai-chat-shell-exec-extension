# Agent Guide

## Purpose

AI Chat Shell Exec is a no-build Chrome/Chromium Manifest V3 extension plus a local Node.js server. It lets AI chat pages run explicit ai-helper shell blocks through the default `ForAI:host` tmux pane, send board helper commands to `ForAI:board`, or write ai-helper file blocks into a configured local directory, then posts results back into the chat as `shell-output`.

Flow:

```text
AI chat page -> extension/src/content.js -> extension/src/background.js -> ws://127.0.0.1:17371/shell -> server/shell_server.js -> tmux pane
```

Treat this project as security-sensitive local remote-code execution.

## Repo Layout

- `extension/`: unpacked Chrome extension files.
- `extension/src/content.js`: page activation, helper block scanning/parsing, duplicate suppression, composer insertion, floating panel, per-origin binding.
- `extension/src/background.js`: settings defaults and migrations, health checks, browser-side call ledger, WebSocket forwarding.
- `extension/src/popup.js`: popup settings UI, tmux target display, config export/import.
- `server/shell_server.js`: local health/WebSocket server, default `ForAI` tmux workspace management, board target resolution, tmux command execution, persistent server ledger.
- `scripts/`: foreground server startup, legacy macOS LaunchAgent cleanup, and cross-platform dev/test/release helpers.
- `tests/`: standalone Node.js tests. There is no `package.json` or central test runner.
- `docs/AI_INSTRUCTIONS.md`: instructions for chat models to emit ai-helper blocks; this is not a coding-agent guide.
- `docs/FEATURE_TEST_MATRIX.md`: required feature-to-test table. Update it whenever a feature, invariant, or `tests/*.test.js` case changes.
- `docs/release-assets/v*/extension-panel-*.png`: README panel screenshots generated by the real Chrome E2E screenshot-stage path. Keep the latest README state table and `tests/readme_panel_screenshots.test.js` aligned with these committed assets.

## Common Commands

Run all automated tests:

```sh
./scripts/test_all.sh
```

The full test runner includes static checks, shell syntax checks, `git diff --check`, every `tests/*.test.js` file, and `tests/chrome_extension_e2e.test.js`, which launches a real Chromium-family browser with the unpacked extension and drives the local tmux test page. On Ubuntu it needs `DISPLAY`, Xvfb, or a cached Playwright Chromium browser; on macOS it can use Chrome for Testing, Chromium, Microsoft Edge, or Google Chrome. Set `CHROME_BIN` to force the browser binary.

Run a single test:

```sh
node tests/manifest_consistency.test.js
```

Run the shell server in the foreground:

```sh
./scripts/start_shell_server.sh
```

Run environment diagnostics:

```sh
./scripts/doctor.sh
```

Manual browser test flow:

```sh
node scripts/start_tmux_test_page_https.js
./scripts/open_tmux_test_chrome.sh
```

Remove any legacy macOS LaunchAgent and start the current foreground server:

```sh
./scripts/install_shell_server_agent.sh
```

Package a release:

```sh
./scripts/package_release.sh
```

`scripts/package_release.sh` refuses dirty worktrees unless `ALLOW_DIRTY=1`.

## Important Invariants

- There are two manifests: `manifest.json` at the repo root and `extension/manifest.json`. Keep them behaviorally aligned; `tests/manifest_consistency.test.js` enforces this.
- The extension ID is pinned by the manifest key: `lkmeogidbglhedgekjgbpbfjkpapnhke`.
- The local server accepts only `chrome-extension://lkmeogidbglhedgekjgbpbfjkpapnhke` by default. `AI_CHAT_SHELL_ALLOW_UNTRUSTED_ORIGINS=1` is only for local development tests.
- The WebSocket server is fixed at `127.0.0.1:17371`; the manual HTTPS test page defaults to `https://localhost:17443/tmux-test-page.html`.
- Default enabled hosts and chain limit are duplicated in `extension/src/background.js`, `extension/src/content.js`, and `extension/src/popup.js`. Current defaults are `["chatgpt.com", "m365.cloud.microsoft"]` and `maxChainCalls = 100`; `tests/default_enabled_hosts.test.js` enforces this.
- Shell helpers must use the plain text block format: first line `ai-helper-shell-start` or `ai-helper-shell-start:<identity>`, command body on every following line, final line `ai-helper-shell-end`. Shell helpers do not include a target line; Role=None runs in the default `ForAI:host`, while an active Master/Slave tab runs in `ForAI-<agentId>:host`. JSON `shell-call` code blocks and `ai-helper-start-shell` aliases are intentionally not supported.
- File helpers use `ai-helper-file-start` or `ai-helper-file-start:<identity>`, a second-line file name, exact file content, and `ai-helper-file-end`; the server writes only a single file name directly under `AI_HELPER_FILE_PATH` when that environment variable exists, otherwise under `$HOME/Downloads`. An explicitly configured empty `AI_HELPER_FILE_PATH` is invalid.
- `AI_CHAT_SHELL_ENV_FILE` optionally names one real, non-symlinked, bounded UTF-8 declaration file. It is parsed as data, never sourced, and freshly overlaid on ai-helper shell command subprocesses, trusted Skill `install.sh`/`uninstall.sh` subprocesses, and Skill load expansion. Every env-file name is load-eligible without a duplicate allowlist entry and overrides a same-named process value, while `AI_HELPER_SKILL_ENV_ALLOWLIST` continues to govern extra process-environment names. Invalid files fail before the affected operation; values never enter health, logs, ledgers, file/board helpers, or the server process environment. Only values actually referenced by an installed `SKILL.md` placeholder may enter its bounded AI load reply; unreferenced values remain absent. Claude runtime placeholders stay literal, server-owned Skill-root placeholders cannot be spoofed, and expansion remains one-pass. Shell injection reuses the private mode-0700 transient tmux runner script and its best-effort normal/recovery cleanup. The exact file-content SHA is part of shell execution dedup identity so an environment change cannot inherit an old completion proof; environment-only changes never alter the raw Skill catalog SHA/version.
- Draw.io helpers use `ai-helper-drawio-start` or `ai-helper-drawio-start:<identity>`, the complete native `<mxfile>` XML body, and `ai-helper-drawio-end`. They are non-executable extension-local artifacts: never forward them to background/server/tmux and never claim the AI can see the render. After scan quiet, select only the last complete candidate, independently of the optional global author-role filter while rejecting explicitly identified user messages. Render valid XML with the pinned packaged viewer in the sandboxed `drawio/viewer.html` iframe; a changed artifact may retain the old SVG only while fresh staging is pending. Keep that cross-origin staging iframe intersecting the viewport while transparent, noninteractive, and `aria-hidden`; moving it offscreen can make Chromium freeze both asynchronous SVG layout and its own failure timers. Sandbox startup and render acceptance have separate visible-page-time checks, iframe load recovers a lost ready message, and a first acceptance timeout gets one fresh iframe retry. A final attempt that never acknowledges `render-started` fails within its visible-time acceptance budget; once `render-started` is received before packaged rendering begins, the parent deadline is cancelled and the isolated viewer detects synchronous or asynchronous SVG output under its own visible-time check. Every latest-candidate decision must supersede a different staging renderer, including an already-current artifact or a cached invalid/render-failure outcome; restoring a cached failure must not enqueue or count the same error again. Fresh success atomically becomes the sole SVG and clears old errors without a composer reply. Validation or final renderer failure must clear the old SVG/download, expose only the latest bounded preview plus browser-console diagnostic, and enqueue one bounded error reply through the existing persistent one-write composer-delivery path. Bind render completion and error delivery to the exact originating candidate/turn before and after settings, local-state load/persist, and composer-attempt awaits; only one proven ChatGPT `/` to `/c` or `/uc` assignment may rebase that ownership, while transcript replacement, permanent-chat navigation, and a second route fail closed. Same XML outcomes are idempotent across DOM redraws; Close/Reopen never rescans or contacts a backend. The preview Maximize/Restore control fills the browser viewport without invoking browser fullscreen permission. Keep the pinned viewer's Apache-2.0 license, attribution, hash, and upstream asset/trademark terms in `extension/vendor/drawio/` plus `THIRD_PARTY_NOTICES.md`; the Chrome extension release ZIP must include `drawio/` and `vendor/`.
- Skill helpers are non-executable high-level catalog requests. The shell server alone discovers configured Claude-compatible `SKILL.md` files, computes raw per-file SHA-256 values and one aggregate SHA, persists a schema-validated monotonic local catalog version, validates exact id/SHA loads, and performs only one-pass allowlisted environment substitution. Every discovered Skill starts uninstalled. The fixed mode-0600 schema-v2 `skill-install-state.json` under `AI_CHAT_SHELL_STATE_DIR` records current Skill/installer SHA state plus server-authenticated receipts backed by a separate private key; only a complete valid authoritative add/delete/modify scan may reconcile it, while a partial/invalid scan must remain read-only and must never erase authenticated receipts or replace the last authoritative catalog state. SKILL.md or installer changes in a valid scan reset installation, forged installed state fails closed, and meaningful validated JSON/installed-set changes advance the monotonic version without creating an effective SHA. `View Skills` must show exactly one management row for every successfully discovered Skill regardless of installation state or the smaller AI/composer catalog-size bound; `installed` is row status only, while invalid files remain explicit diagnostics. An already-open management dialog must refresh latest-only across tabs when catalog version/SHA/count changes, without stale-response rollback or composer writes. Only installed Skills may enter the AI catalog or load. The management UI alone may request install or uninstall after a trusted click and native confirmation; it sends exact id/Skill SHA/lifecycle-script SHA/catalog SHA. The server serially reads a safe real adjacent `install.sh` or optional `uninstall.sh` through a no-follow descriptor, validates inode/hash/root containment, executes a private immutable snapshot through fixed `/bin/sh` argv with Skill-directory cwd and a minimal base environment plus the optional freshly parsed execution environment, retains a bounded stdout/stderr tail, and removes the snapshot. Install success additionally requires fresh unchanged Skill/installer proofs. Exit-0 uninstall atomically clears the exact installed record before refreshing the catalog, including when that successful script changed lifecycle files. Nonzero, signal, idle timeout, launch failure, or state-write failure does not proactively clear an unchanged installed identity; normal receipt reconciliation still resets an identity changed by the failed script or another writer. Lifecycle execution has no absolute runtime cutoff: either output stream resets a shared idle clock, including after capture saturation, and 600 consecutive seconds without stdout/stderr terminates the whole process group. Main-shell exit and idle kill both have bounded stdio/process-group settlement so descendants cannot hold the serialized queue forever. The browser gives both lifecycle messages no absolute WebSocket watchdog and uses the 20-second heartbeat. AI helpers cannot install or uninstall. Install/uninstall/list/load/rescan never touch tmux, command ledgers, or Force run. Server-owned `AI_HELPER_SKILL_ROOTS_JSON` and `AI_HELPER_SKILL_ROOT_SOURCE` runtime placeholders inject authoritative resolved non-secret root metadata only into explicitly loaded Skill bodies that request it; process environment values must never spoof them, and expansion must enforce its output budget before allocation. Automatic status uses a short cached snapshot, while explicit management/list/install/uninstall/load/rescan and final ACK validation force a fresh bounded scan; root count, visited entries, diagnostics, file count/depth/per-file/total-byte, and actual serialized-catalog limits must fail closed before composer persistence can truncate or amplify a successful response. Nonzero/signal/idle-timeout diagnostics may travel only in the direct trusted lifecycle response: background immediately sanitizes them into a bounded one-use in-memory record, removes them before answering the content script, and an owner-tab request opens a separate `chrome-extension://` result window that consumes the record. Lifecycle output must never enter the chat page DOM, composer/pending deliveries, AI protocol replies, ledgers, logs, management/health responses, install-state JSON, or persistent/session storage. Synchronization is origin-scoped and latest-only across tabs, uses the fixed `AI_CHAT_SHELL_SKILLS_CATALOG` memory entry, preserves each installed Skill's full description as non-instruction routing metadata, requires the AI ACK to echo the exact catalog SHA and version, rejects stale challenges/SHA/version values and explicitly recognized user messages including M365 `.fai-UserMessage` descendants, and keeps failed syncs visibly pending. When a host's rendered `innerText` corrupts one otherwise canonical Skill field with layout-only line breaks, content may fall back to the same node's `textContent` only if both representations are line-break-equivalent, each contains exactly one complete Skill envelope, any explicit identity agrees, rendered validation fails, and canonical validation succeeds; real naked numeric lines and hidden extra content remain rejected before backend work. An explicit force may replace only the same owner tab's lost challenge and discards only stale, never-written Skill sync deliveries; an obsolete in-flight queued response carries a durable discard marker so an immediate reload cannot revive it, while an already-inserted response remains owned and is not rewritten. Closed tabs must not leave orphan ownership. Runtime sync prompts carry their complete interaction contract but must not contain a complete `ai-helper-skill-start` or `ai-helper-skill-end` marker; stable AI instructions describe only when/how to load installed Skills.
- Helper identity suffixes are optional simple no-space values used for request diagnostics. Unsuffixed helper blocks derive identity from a stable plain text payload hash; neither form controls server execution dedup.
- Board target resolution and internal diagnostics accept pane id, `session:window.pane` address, or a unique window name. Ambiguous window names must not resolve. Shell helper targets are intentionally ignored.
- The shell server is the sole command-duplicate authority. After resolving the actual tmux pane it fingerprints the tmux server/pane plus the current pane shell PID, command, and actual cwd; only a command with a server-controlled completion proof may return `duplicate: true`. A `respawn-pane` shell therefore starts with no inherited duplicate history even though its pane id is unchanged, and missing pane-shell identity disables dedup. Ctrl+C after the executed marker produces prompt exit-130 completion and counts as executed history; interruption before that marker remains retryable through a newly rendered helper. Generic board prompt text is spoofable, so it is neither duplicate authority nor a strong serialization proof; shell-backed boards additionally use foreground-process-group readiness. Browser local storage key `shellCallLedger:v1` is non-blocking audit state. The content script scan-debounces the exact rendered helper and, after any shell/board backend response, persists pending composer delivery instead of resending the same run; recycled/new render roots remain eligible for backend adjudication. Failed, cancelled-before-execution, timed-out/unconfirmed, unavailable-target, transport, incomplete-pane-identity, board, and merely `running` calls never become duplicate authority; immutable internal attempt ids prevent client call-key collisions; force runs bypass authoritative server dedup while recording `forced: true`.
- Shell helper runners and direct Terminal vision test runs are serialized per resolved tmux pane instance. Queue identity uses the stable tmux socket + server pid + pane id, never mutable window addresses, names, indexes, or session metadata; a tokenized tmux pane option persists ownership across shell-server restarts. A request from a refreshed page waits behind the old page's still-running command without consuming its own runner output-idle timeout. The timeout defaults to 3 minutes, resets on observable command-output changes, and enters persistent `awaiting-user` state instead of returning a false result; Continue resets the clock, while the role-scoped Stop helper must revalidate the exact owner, exact waiting execution when known, and foreground process group before signaling. Manual-busy readiness is authoritative only for child work proved by tmux pane PID/TTY and foreground process-group metadata; missing metadata must fail closed and remain retryable. The root interactive shell's own blocking builtins (such as direct `read` or a pure-builtin loop) cannot be distinguished from its prompt without shell hooks, so use a script/child shell or dedicated pane. Capture cwd and create the authoritative command claim only after the request reaches the queue head and the pane instance is revalidated. Never send multiple runner command lines into one observed busy pane. Different pane instances remain concurrent.
- The floating panel is compact and state-driven by default: normal idle shows concise status, an always-visible saved-role badge (`None`, `Master`, or `Slave`), the local Skills version chip, and More. The header Skills chip is never replaced by Force run. Server Check appears on an error. A detected executable or Skill helper starts one 20-second accumulated semantic-idle clock keyed by page lifecycle, helper kind, and payload semantic hash; repeated scans and equivalent DOM redraws must not reset it, while only a real helper/backend operation pauses and later resumes it. At the deadline the compact action row exposes generic Force run; an actionable Skill may expose Process Skill before that deadline. More's Setup & recovery group always contains a Force run entry, disabled only when no eligible helper exists or an operation is active. Both Force run and Process Skill must require a real trusted browser click; host-page `.click()`/synthetic events must fail closed before backend or local Skill work. Stop helper replaces recovery actions during active shell execution. A current acknowledged Skills chip remains clickable and opens only the local catalog, an update chip starts synchronization, and a syncing chip stays disabled. Existing setup/recovery (including an always-available Server Check), Agent/tmux-ai, Skills, full-status/debug, and page-binding controls remain present under five labelled advanced groups and are never removed merely to reduce the default footprint; Page binding is the last group and uses a default-closed native details control. Draw.io is a contextual action: hidden until a preview artifact or error log exists, then retained for reopening after Close. The output-idle notice adds only contextual Continue waiting; Stop helper remains the single user-facing termination concept.
- Chrome 116 is the minimum supported browser version. Long WebSocket operations send a heartbeat every 20 seconds. If an MV3 runtime-channel/service-worker loss drops the response while the page survives, content polls the server's read-only, kind-scoped `run-status` using the same call key; it must never resend `run` or `run-board`. A full reload creates a new call key and relies on the persistent pane lease plus backend adjudication when the helper is rendered again. Each actual execution has a canonical `executionId`; duplicate chains inherit it, and a `run-result-presented` receipt distinguishes an already-presented result from clean recovery of an unpresented bounded replay. Presentation is monotonic across the canonical chain, including status recovery of duplicate entries created before a later receipt. Authoritative duplicate diagnostics are local-only and must never enter the composer/model. Persistent ownership must be bound to the immutable queued attempt before authoritative adjudication, nonterminal ledger entries must survive count pruning, and late failures must not downgrade terminal completion. Completed stdout/stderr have per-result and global replay bounds in the server ledger.
- ChatGPT's one-time provisional `/` to permanent `/c` or `/uc` assignment may carry an automatically detected in-flight helper only when its exact candidate/turn proof remains current. Carry the active execution lock, revalidate after settings/approval/backend/storage awaits and both before and after every shell/board recovery-status await, stage the result until the assigned route settles, and fail closed on transcript replacement, an already-permanent or second route, detach, or semantic change. Pending creation must revalidate after both state loading and durable persistence; a stale continuation may delete and persist cleanup only when the map still contains the exact entry object it created, never a same-call replacement, and must not overwrite a newer active status. A queued, inserted, or submitted-unconfirmed non-Skill delivery may cross a route only while its live volatile exact-origin guard successfully rebases; restored ordinary entries have no such proof and fail closed even on `/` to `/c` or `/uc`. Submitted/presented entries may cross solely for presentation-receipt cleanup, with composer and old-status side effects disabled. Runtime recovery remains status-only and never resends the original backend request; Force backend and validation results retain their strict original route boundary through pending persistence. This route ownership layer must not modify the pinned send actuator.
- Frontend `activeCallId` covers backend execution only, never the potentially slow composer auto-send calibration loop. Every successful helper response enters a bounded per-tab persistent pending-delivery queue before composer work; retries are local and preserve exact ownership. Each delivery may automatically write its content into the composer at most once. Any composer containing user characters before that write is a conflict, including whitespace-only or text exactly equal to the pending delivery; host-only empty paragraph/newline structure is not user content. If the user removes or replaces plugin-written text, cancel the current queued helper-output batch; never reinsert it, never mark it presented, and let only a genuinely new rendered helper create a fresh delivery. A framework redraw that replaces the composer DOM node is not user cancellation when the current visible composer still contains the exact plugin-owned text; transfer send ownership to that node without another write. Before the first write, a stale non-explicit weak remembered page input must yield to a currently visible strong chat composer; an explicit Bind input selection remains authoritative. The active actuator continuously proves its node is still the current visible composer, rejects every competing visible non-empty strong reply draft regardless of focus or candidate score, and treats an actively edited ambiguous textarea fail-closed; an inactive generic tool/side-panel textarea is not itself a reply-draft veto. It captures both document and original-subtree events and aborts its old 80-round loop at the next await boundary after ownership loss. It permits at most one bounded exact-text composer-node handoff; detached/hidden nodes, trusted user mutations, and replacement user drafts lose send authority. Its per-lifecycle generation is recorded synchronously after the final guard preflight and immediately before the first original actuator call; best-effort storage persistence must never introduce an awaited pre-actuator gap. After the first write, the persistent queue may observe manual submission or retry after an actual same-tab route lifecycle change, but it must not restart the v0.8.9 send actuator repeatedly within one page lifecycle; it must never repeat the backend operation or composer write. A cleared/changed composer, an auto-send-disabled insertion, and the original actuator's `sent` heuristic are not presentation proof: only a fresh matching submitted-user-message count may create the local tombstone and canonical `run-result-presented` receipt. The v0.8.9 actuator's 125/150ms waits use a bounded background message clock so its original 80-round behavior is not stretched indefinitely by hidden-tab timer throttling. A pending-delivery route handoff, including a result still in `queued` phase after its backend response, carries the prior rendered-helper proof so the same DOM helper cannot re-execute solely because its URL changed; a genuinely new route without pending ownership remains eligible. Inbound agent prompts follow the same one-write and redraw rules: actual removal, replacement, or navigation after writing cancels composer delivery and may retry only the local hub cancellation acknowledgement. The outer delivery lifecycle validates exact plugin-owned text and the current visible composer before invoking auto-send, and its capture guard blocks stale button/form/keyboard events if ownership or lifecycle changes while the original loop is running. On exactly `m365.cloud.microsoft`, only a post-write delivery lifecycle may treat M365 Lexical's exact newline removal plus trailing `U+200B U+200C` caret sentinel as the same plugin-owned text; the pre-write occupied-composer check remains strict. Fresh `.fai-UserMessage[role="article"]` roots prove ordinary submission by exact whole-message comparison. Because M365 irreversibly serializes extension-inserted known structured payloads (fenced `shell-output` or identity-bearing agent prompts) into one newline-free text node, their strict no-trim host-serialization equivalence is accepted only as a fresh before/after count inside the plugin-owned delivery lifecycle. The five send-actuator functions themselves are intentionally pinned byte-for-byte to v0.8.9 and are also byte-identical to v0.8.6; do not add click budgets, association filters, or fallback changes without explicit user authorization. A pending agent delivery defers, but does not mark or consume, a newly detected helper; submitted agent prompts are acked without reinsertion, identical agent-message response-loss retries are idempotent, and a page-agent profile change cancels the old delivery lifecycle.
- Treat shell, board, and vision command bodies as opaque executable text after their helper envelopes have been parsed. Never classify or reject a command because its body contains `shell-output`, Markdown fences, terminal-prompt text such as `$ ...`, result headings, metadata labels, or helper markers; these are all valid inside scripts, strings, comments, and heredocs. Prevent feedback loops from exact rendered provenance instead: an automatically scanned helper structurally inside a fenced/DOM `shell-output` block is suppressed, while an explicit Force run may execute it. Keep repeated-command control in the authoritative server dedup and chain-limit mechanisms.
- `content.js` has tests that match specific function names and source text for force-run behavior. Rename/refactor those areas carefully.
- `server/shell_server.js` exports helper functions used directly by tests. Preserve exports when changing tmux or WebSocket logic.
- Shell-output formatting uses `cmdHash` for long or multiline commands so users and tests can diagnose command identity; server execution dedup uses the full received command after pane resolution.
- The server writes transient tmux scripts under `.state/tmux-runs` and removes them best-effort.
- A host may forbid `chrome-extension://` iframe navigation with `frame-src 'self'`. When the current document supplies a valid `script-src` nonce, Draw.io must preserve the same `sandbox="allow-scripts"` boundary by using a fixed nonce-authorized `srcdoc` that contains only packaged CSS/scripts and a generated channel; raw XML still crosses only the channel-bound `postMessage` request. Validate the nonce and channel before building HTML, disclose no referrer, never add `allow-same-origin`, and retain the packaged extension-page fallback for hosts without a usable nonce. The real-browser suite must keep an independent CSP page that proves this path.
- `docs/FEATURE_TEST_MATRIX.md` must list every product feature or invariant and every `tests/*.test.js` case. Keep the table current in the same change as code or test edits; `tests/feature_test_matrix.test.js` enforces that every test file appears there.

## Development Notes

- Keep an independent expert-testing seat for every fix and feature. That reviewer must add or verify dedicated positive and negative regression cases (plus boundary, race, or recovery cases when relevant), cross-check the implementation against `docs/FEATURE_TEST_MATRIX.md`, and report gaps before release. Do not treat an existing broad E2E as a substitute for a focused regression case.
- After changing extension files, reload the unpacked extension in `chrome://extensions` and refresh any affected chat tabs.
- After changing server files, restart the foreground server.
- The installer compatibility script is macOS-specific and uses `launchctl` only to remove old LaunchAgents before starting the foreground `./scripts/start_shell_server.sh` flow. Ubuntu uses the foreground server flow unless the user adds their own service wrapper.
- `.state/`, `dist/`, `build/`, logs, and `node_modules/` are ignored.
- Prefer small, focused tests that exercise the standalone Node modules or VM-loaded extension scripts.
